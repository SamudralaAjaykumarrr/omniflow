# Risk Register

Last updated: 2026-07-26 (Phase 6 streaming-data-platform hardening branch —
see `docs/phase-6-streaming-data-platform.md`; risk #19 closed, #21/#22
added). Status values: `Open`, `Mitigated`, `Accepted`, `Closed`.

| # | Risk | Impact | Mitigation | Status |
|---|---|---|---|---|
| 1 | Scope vs. depth — the literal spec is multi-week/multi-engineer scope if every section is built to uniform "production-grade" depth | Could produce a pile of half-finished stubs instead of a coherent demo | 13-phase staged plan, each phase additive and independently runnable/verifiable; "thin but real" rule; stretch items (Prophet/XGBoost, EKS, large-scale load test) explicitly named as optional upgrades, not silently promised | Open — being actively managed phase by phase |
| 2 | Resource ceiling — Redpanda + Postgres + MinIO + Spark + Prometheus/Grafana/Jaeger + backend services + frontend on 15Gi RAM / 8 CPU | Local demo could be too slow or OOM | Redpanda instead of Kafka+ZooKeeper (ADR 0001), single-node Spark (ADR 0005), lean container images | Confirmed through Phase 4 — MinIO + Bronze/Silver/Gold/lag-poller ran alongside the full Phase 1-3 stack (23 containers total) without OOM; running Silver's 11 and Gold's 9 genuinely *concurrent* Structured Streaming queries against too few Spark cores did starve individual queries under real load (see risk #16) — the resource ceiling risk is real, not just theoretical, and needed an actual fix, not just headroom |
| 3 | No host Python/Node/Java/Terraform | Slower dev/test iteration, all through Docker | Multi-stage Dockerfiles with cached dependency layers; will ask the user before installing anything system-wide if Docker-only iteration proves too slow | Accepted — confirmed workable in Phase 1, all builds/tests/lint ran through Docker only |
| 4 | Fabrication risk on forecasting/load-test/coverage numbers | Spec explicitly forbids fabricated performance claims; false numbers would undermine the project's credibility as a portfolio piece | Every number in `TEST_RESULTS.md`/`docs/resume-evidence.md` is generated by an actual command run in this session, cross-checked before commit | Open — enforced at every phase close-out |
| 5 | Terraform/paid-service boundary | Any real `terraform apply`, AWS credential use, or paid API key would be a real-money, hard-to-reverse action taken without explicit authorization | Terraform authored + `fmt`/`validate` only, never applied (ADR 0007); this is a hard stop-and-ask boundary, not a judgment call made per-phase | Accepted — standing constraint for the whole project |
| 6 | Cross-document consistency drift (event catalog vs. data model vs. architecture diagrams) as the build progresses | Docs could silently diverge from what's actually implemented, undermining the "clear architecture communication" goal | Each phase close-out includes a docs-update step before commit; Phase 13 includes an explicit final consistency pass | Open |
| 7 | Data quality / referential integrity across service-owned tables (Order vs. Inventory schemas, no live cross-service FKs) | Orphaned/inconsistent IDs between services could go unnoticed | Application-level validation at write time + `app.dq.checks`/`app.dq.report`'s Bronze-vs-Silver reconciliation, schema-rejection-rate, duplicate-rate, late-event-rate, and freshness checks, run against real MinIO data and verified `PASS` in Phase 4 | Mitigated — folded into Phase 4 rather than a separate Phase 5, since the Spark plumbing to build DQ checks on was already in place; original Phase 5 slot is now redundant with this |
| 8 | Saga orchestrator is custom, not a proven framework (ADR 0004) | Less battle-tested than Temporal for genuinely large-scale/long-running workflows | Explicitly documented as the scope tradeoff in ADR 0004 and the interview guide's "what I'd improve for enterprise scale" section, not hidden | Accepted |
| 9 | Docker `ENTRYPOINT` scripts that unconditionally run their own hardcoded command ignore whatever command Compose/`docker run` passes them (`sh -c "pytest ..."` silently got swallowed and the API server started instead) | Any future service Dockerfile with a migration-then-serve entrypoint could reintroduce this and make `docker compose run ... <test command>` silently run the server instead of tests, with no error — just a hung/idle container | Both `entrypoint.sh` scripts now `exec "$@"` when arguments are passed, only defaulting to serving uvicorn with none; caught and fixed during Phase 1 test verification, before any test result was trusted | Mitigated |
| 10 | Shared mutable test state across a session (one `app`/middleware singleton reused by every test via a shared fixture) can make a test's outcome depend on test execution order, not just its own logic | A rate-limit or similar stateful-middleware test can pass or fail based on how many requests earlier, unrelated tests happened to make — a flaky-by-order test, not a real bug | Reset the shared counter explicitly at the top of the test that depends on it (`app.state.rate_limit_hits.clear()`), and state lives on `app.state` specifically so it's reachable from tests rather than buried in a middleware-instance attribute | Mitigated |
| 11 | Saga resume gap: if the orchestrator process crashes strictly between a reservation succeeding over REST and the `SELECT_AND_RESERVE` step's local commit, there is no local record of that reservation | A resumed saga could double-reserve, or (as currently implemented) fail loudly and require manual intervention rather than completing automatically | Deliberately accepted rather than solved this phase — closing it for real needs idempotency keys on Inventory Service's reservation endpoint tied to `(order_id, sku, saga_step)`. Current behavior fails loud with a clear `last_error` instead of silently double-reserving or guessing (see ADR 0010, `app.saga._step_select_and_reserve`) | Accepted — named as the top "what I'd improve" item in the eventual interview guide |
| 12 | Test-conftest schema management (`Base.metadata.create_all`/`drop_all`) coexisting with real Alembic migrations run automatically by every service's entrypoint | A future migration could again desync `alembic_version` from actual table state if a service's test fixtures still drop tables Alembic thinks are already migrated (exactly what happened in Phase 2, risk/decision recorded in `DECISIONS.md`) | Every service's test schema fixture now only truncates (never drops) at session start; `CLAUDE.md`/this file call it out explicitly for future phases adding migrations | Mitigated |
| 13 | Gateway rate limiting and connection pooling are single-instance-only (in-process counter, per-process DB engine) | Would not work correctly if any service were horizontally scaled to multiple replicas without a shared backing store (Redis, PgBouncer) | Explicitly out of scope for a single-instance local demo; named here and in the interview guide as the first thing to change for real horizontal scale | Accepted |
| 14 | Grafana runs with anonymous admin access (`GF_AUTH_ANONYMOUS_ENABLED`) and every worker's standalone Prometheus `/metrics` server is unauthenticated | Fine for a single-instance local demo where nothing here guards real data (ADR 0009's authn/authz scoping already excludes the observability stack); would leak internal metrics/dashboards if ever exposed beyond localhost | Explicitly local-demo-only; named here as the first thing to change (real Grafana login, network-restrict `/metrics`) before any shared or internet-facing deployment | Accepted |
| 15 | `make typecheck` (mypy) is new this phase, non-strict (`--ignore-missing-imports`), and not yet wired into any CI pipeline (Phase 12 lands CI) | A typing regression introduced between now and Phase 12 wouldn't be caught automatically — only by someone remembering to run `make typecheck` manually | Documented here so Phase 12's CI workflow definitely includes it, not just lint/format/test | Open — mitigation lands in Phase 12 |
| 16 | 11 (Silver) / 9 (Gold) genuinely concurrent Structured Streaming queries in one SparkSession, sharing a small core count, can hit Spark's default FIFO job scheduler and starve an individual query of scheduled time indefinitely (not just lag) — hit for real running the generator against this host, `order.created`'s Silver query stopped advancing entirely | A demo run could silently under-report Bronze/Silver counts if this regresses (e.g. a future phase adds more concurrent queries without re-checking) | `build_spark_session` defaults to `local[*]` (matching ADR 0005, which the code had drifted from) plus `spark.scheduler.mode=FAIR`; verified fixed by an extended real run (`app.dq.report`'s reconciliation check reached exactly 0 after the fix, vs. 15-32 before it) | Mitigated |
| 17 | The synthetic generator (`app.generator`) publishes onto the real Kafka topics `order-service`/`inventory-service`/`fulfillment-orchestrator`'s real consumers subscribe to (deliberate — Bronze consumes the real event catalog either way) | Running the generator alongside the real stack makes those real consumers also process synthetic events; a real consumer's logs will show expected `404 Not Found` responses looking up a synthetic order ID that doesn't exist in Postgres | Confirmed harmless in Phase 4's compose verification: zero dead letters produced, no errors, at-least-once/idempotent consumer design absorbs it cleanly — named here so this doesn't read as a real bug when reviewing logs after running the generator | Accepted |
| 18 | Gold's live streaming queries maintain a `_spark_metadata` sink commit log (Structured Streaming's `FileStreamSink`); any metadata-aware batch reader only sees files recorded in it, so any *future* tool that writes real Parquet files directly into a Gold path via raw S3 operations (bypassing that log) would produce files that are physically present but invisible to normal reads — the exact bug `app.backfill`'s swap step hit before Gold was switched to `foreachBatch` writes (which never create that log) | A new tool touching Gold's output paths outside `app.gold.runner`/`app.backfill` could reintroduce an invisible-write bug without realizing it | Documented here and in `DECISIONS.md`; the fix (foreachBatch, not `.writeStream.format("parquet")`) is the pattern to follow for any *other* future Structured Streaming sink added to this codebase, not just Gold | Accepted — architectural pattern to preserve, not something with further work pending |
| 19 | `docker-compose.yml`'s `spark-bronze`/`spark-silver`/`spark-gold` services already declare a `METRICS_PORT` env var and `expose` that port (pre-existing scaffolding from before this phase's work began), but no `app.bronze`/`app.silver`/`app.gold.runner` code actually starts a `prometheus_client` HTTP server on it, and `infra/docker/prometheus/prometheus.yml` has no scrape target for any of them — unlike every Phase 3 background worker, which does both | The data platform has zero Prometheus/Grafana visibility right now — a stalled or crashed Spark job (like risk #16, before it was fixed) is invisible to the observability stack and only discoverable via `docker compose logs`/`docker compose ps` | **Fixed** (branch `phase-6-streaming-data-platform`): `app.metrics.start_metrics_server` (backed by `prometheus_client`, now a real dependency) runs in every Bronze/Silver/Gold `main()`; `data_platform_batch_rows_total`/`data_platform_batch_duration_seconds` recorded per batch; three new Prometheus scrape targets added. `lag-poller` intentionally excluded (not a Spark job, no `METRICS_PORT` declared for it). See `docs/phase-6-streaming-data-platform.md` section B | Closed |
| 20 | `make security` (Phase 5, real `pip-audit` run against every service's pinned `requirements.txt`) found 14 known CVEs across 4 packages: `pip` 25.0.1 (5 CVEs, wheel/tar extraction path traversal — fixed outright by pinning `pip==26.1.2` in every Dockerfile, not accepted as a risk), `pytest` 8.3.3 (`PYSEC-2026-1845`, local `/tmp/pytest-of-{user}` collision — a test-only dependency baked into runtime images, exploitable only by another local user on the same host, which doesn't exist in a single-process container), `pyarrow` 17.0.0 (`PYSEC-2026-113`, a C++ use-after-free — the advisory itself states the vulnerable API "is not exposed in language bindings (Python, Ruby, C GLib)", so this codebase's pyarrow usage cannot reach it), and `starlette` 0.38.6 pulled in transitively by `fastapi==0.115.0` across all four HTTP services (7 CVEs: `PYSEC-2026-{161,248,249,1941,1943,2280,2281}` — host-header/path confusion, HTTPEndpoint method confusion, and two unbounded-form-data DoS variants) | The starlette CVEs are the substantive one: host-header confusion could enable auth bypass in code that trusts `request.url.hostname`/`.netloc`, and the DoS variants could exhaust memory via oversized form bodies | Verified (`pip install fastapi==0.115.0 starlette==0.40.0` → `ResolutionImpossible`) that fixing these needs starlette >=1.0, which this fastapi version cannot resolve against — the real fix is a coordinated `fastapi`/`starlette` major-version upgrade across all four HTTP services with a full re-test pass, scoped as its own follow-up rather than a same-pass dependency bump that risks destabilizing Phase 1-4 work without time to re-verify it. Grepped every service: nothing reads `request.url.hostname`/`.netloc` for authorization (only `.path`, for logging in `api-gateway/app/middleware.py`), and the stack is local-demo-only, never internet-facing (consistent with risk #14's existing posture) — both bound today's practical exploitability. All 9 IDs are pinned in `make security`'s `IGNORE_VULN_FLAGS` with this same rationale inline, and `pip-audit`'s own output reports the ignored count on every run (`"N ignored"`), so they stay visible, not silently dropped | Open — tracked here as the concrete next step (fastapi/starlette major-version upgrade + full re-test) before this stack is ever exposed beyond localhost |
| 21 | `app.silver.build_type_query`'s dedup watermark was declared on `occurred_at_ts` (the event's own business timestamp), not ingestion time. `app.generator.generate_order_lifecycle` legitimately backdates... rather, forward-dates `order.shipped`'s `occurred_at` up to 60 minutes after `order.created`'s (simulated shipping delay — real, meaningful test data, not a generator bug). Found running the Phase 6 smoke test against real Kafka/MinIO data: `app.dq.report`'s reconciliation check failed for `order.shipped` by as much as ~44% in one run | Spark's watermark for a stateful operator (`dropDuplicatesWithinWatermark`) advances to `max(event time seen) - threshold`; **any** row (not just duplicates) whose watermark-column value trails that already-advanced watermark is silently dropped by Spark itself, upstream of the write batch — not quarantined, not counted late, just gone. One high-latency `order.shipped` event could advance the watermark far enough to silently drop a different, valid, lower-latency one processed afterward | **Fixed** (branch `phase-6-streaming-data-platform`): watermark moved to `ingested_at` (Bronze's `F.current_timestamp()` at write time), which only moves forward with real processing time and can't be pushed ahead by a business-modeled delay. Regression test: `tests/test_silver.py::test_dedup_watermark_on_ingested_at_survives_wide_occurred_at_swings`. ~64 rows across 4 event types already silently dropped by the pre-fix code in this session's persistent MinIO volume were recovered via `app.backfill silver --apply` (which dedups with no watermark at all, so was never subject to this bug) — applied with explicit confirmation before the destructive swap step. `app.dq.report` reached `overall: PASS` afterward. Full detail: `docs/phase-6-streaming-data-platform.md` section D, `DECISIONS.md` | Closed |
| 22 | `Trigger.AvailableNow()` (`--once` mode, used by every `app.bronze`/`app.silver`/`app.gold.runner --once` invocation) gives no guaranteed extra "flush" cycle after the last micro-batch that contains new data for a given per-event-type Silver query. Verified empirically, not assumed: reconciliation gaps left by the final `--once` micro-batch of a run (e.g. `order.shipped`, ~18-25 rows in separate observed runs) did **not** shrink after waiting 25+ minutes with no new traffic — well past `DEDUP_WATERMARK` (10 minutes) — with a repeated `silver --once` run in between finding nothing new to process. This rules out "just needs to wait out the watermark"; the pending, watermark-gated output for that final batch appears to simply never get a subsequent trigger to re-evaluate and emit it once `availableNow` decides there's no more source data | A `--once`-driven pipeline (smoke tests, ad hoc single-shot runs) can leave a small, real, non-self-healing gap in Silver for whichever event type's Bronze data was still arriving right as the run ended — invisible until `app.dq.report`'s reconciliation check catches it | Not solved architecturally (would need re-architecting Silver's stop condition, e.g. an explicit trailing settle-and-reprocess step, out of scope for this pass) — recoverable via the tool this class of gap always is: `app.backfill silver --event-type <X> --from-date <Y> --to-date <Y> --apply`, which dedups with a plain `dropDuplicates` and no watermark at all, so is never subject to this. Used for real, twice, in this branch's own validation (`DECISIONS.md`) to reach a genuine `app.dq.report` `overall: PASS`. The long-running, continuously-triggering production services (real `docker compose up`, not `--once`) are far less exposed in practice, since they keep triggering new batches, giving pending state repeated chances to flush — but this wasn't verified to be immune, only less exposed | Open — accepted for this pass; a real fix would change `--once`'s stop condition for stateful queries, which is broader than this branch's scope |
| 23 | Phase 6 (demand forecasting): `app.forecasting.forecast.generate_future_forecast`'s recursive multi-step rollout (each future day's prediction is fed back in as the next day's "actual" so the following day's lag/rolling features have history) initially had a real ordering bug — `current` (the model-input frame, sorted by `build_feature_frame`'s internal grain sort) and `future_df` (built from a separately-derived `last_rows.index`) are not guaranteed to share the same row order, so writing predictions back into `future_df` positionally attached a prediction to the wrong SKU/location series. Found by `tests/forecasting/test_forecast.py::test_generate_future_forecast_recursion_feeds_predictions_forward`'s `_Lag1Model` probe (asserts step 2's prediction exactly equals step 1's) before this ever shipped | A silently-misattributed prediction would corrupt every subsequent recursive step's lag/rolling features for the *wrong* series, compounding across the whole forecast horizon | **Fixed**: predictions are now keyed by `(sku, location_id)` explicitly (a dict lookup) rather than relying on the two DataFrames' row orders matching by position — verified by the same regression test. Separately, the recursive rollout's *inherent* limitation (a lag/rolling-feature model has no native multi-horizon head, so step-to-step prediction error can still compound even with correct wiring) remains a documented, accepted limitation, not something this fix claims to solve — see `docs/phase-6-demand-forecasting.md` 'Limitations' | Closed (the ordering bug); inherent rollout-error-compounding limitation accepted, not solved |
