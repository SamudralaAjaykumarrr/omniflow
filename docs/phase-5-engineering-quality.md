# Phase 5: Engineering quality

This branch (`phase-5-engineering-quality`) adds the tooling a real
production repo is expected to have but this one didn't yet: a measured (not
assumed) coverage threshold, a shared devtools image, zero-cost security
scanning, pre-commit hygiene hooks, and a GitHub Actions CI workflow that
runs the same `make` targets a contributor runs locally.

**Naming note**: `PROJECT_STATUS.md`'s 0-13 phase table already has a
"Phase 5: Data quality," done and folded into Phase 4. This document is
*not* that phase — the branch name collides with it by coincidence. Rather
than renumber a table every other doc cross-references, this work is kept
as its own document and pulls forward a slice of three later phases' scope:
coverage tooling/threshold (Phase 10), dependency/SAST security scanning
(part of Phase 9 — JWT/RBAC finalization is explicitly not in this slice),
and a CI pipeline (Phase 12). See `DECISIONS.md`'s 2026-07-25 entry for the
full rationale. `PROJECT_STATUS.md`'s phase table is not renumbered by this
work.

## What changed

- **`infra/docker/devtools/Dockerfile`** — one pinned image (ruff, mypy,
  pytest, coverage, bandit, pip-audit, pre-commit, plus every service's
  runtime deps at the same versions already used by `make typecheck`) built
  via `make setup-dev`. Used by `coverage`, `security`, `pre-commit` —
  `lint`/`format`/`typecheck` keep their existing self-contained
  `pip install` pattern from Phase 3, unchanged.
- **Root `Makefile`** — added `help`, `setup-dev`, `coverage`, `security`,
  `docker-validate`, `docker-build`, `pre-commit`, `ci`; every `test-*`
  target now also writes a per-service coverage data file into
  `coverage-reports/data/` (consumed by `coverage`, deleted from there by
  `coverage combine`, so it's transient, not committed).
- **`pyproject.toml`** — `[tool.coverage.paths]` (reconciles the two
  absolute roots services vs. event-contracts record coverage under — see
  `DECISIONS.md`), plus the pre-existing `[tool.coverage.run]`/
  `[tool.coverage.report]`/`[tool.ruff.format]`/`[tool.mypy]` sections from
  earlier in this same branch's uncommitted work (kept as-is).
- **`.pre-commit-config.yaml`** — hygiene hooks (trailing whitespace,
  end-of-file, merge conflicts, large files, YAML/JSON/TOML syntax, private
  key detection, line endings) plus `ruff`/`ruff-format`. Deliberately
  excludes mypy and the test suites — those need each service's full
  runtime deps and a live Postgres, too heavy for a hook that should stay
  fast; they run as separate `make typecheck`/`make test` steps, both still
  gated in CI.
- **`.github/workflows/ci.yml`** — one job, `quality-gate`, on the standard
  free `ubuntu-latest` GitHub-hosted runner: checkout, format-check, lint,
  typecheck, setup-dev, coverage (+ upload `coverage.xml` as a build
  artifact), pre-commit, security, docker-validate, docker-build. No paid
  runners, no cloud credentials, no secrets required.
- **Five service Dockerfiles** — added `pip install --upgrade pip==26.1.2`
  as the first step of each build, fixing 5 of the 14 CVEs `make security`
  found on its first real run outright (see Security below).
- **`RISKS.md` #20, `DECISIONS.md`** — the security findings that weren't
  fixed outright, and why.
- **`.gitignore`** — `coverage.xml`, `coverage-reports/` (transient,
  regenerated by `make coverage` every run).
- **Repo hygiene**: removed `docs/imagesq/`, a stray empty untracked
  directory (a typo of `docs/images/` left over from an earlier command).

## Coverage: measured first, then thresholded

`make coverage` runs all six suites with coverage instrumentation on,
combines the six per-service data files into one `coverage.xml` at the repo
root, and enforces `COV_THRESHOLD`. The very first real combined run — no
threshold existed yet to pass or fail against — reported:

| Suite | Stmts | Miss | Cover |
|---|---|---|---|
| event-contracts | 321 | 41 | 87% |
| order-service | 525 | 48 | 91% |
| inventory-service | 469 | 33 | 93% |
| api-gateway | 149 | 10 | 93% |
| fulfillment-orchestrator | 762 | 294 | 61% |
| data-platform | 767 | 423 | 45% |
| **TOTAL** | **2993** | **849** | **71.6%** |

`COV_THRESHOLD := 65` was set *after* seeing this number, a few points
under it rather than at it, so one newly-added untested branch doesn't fail
CI outright. The two suites dragging the average down are both explainable,
not neglected: fulfillment-orchestrator's `main.py`/`middleware.py`/
`routes.py`/`schemas.py`/`outbox_relay.py` (0% each — FastAPI wiring and the
outbox relay loop) and data-platform's `generator.py`/`gold/runner.py`/
`lag_poller.py` (0% each — CLI entrypoints and a live-Kafka poller) all need
a live Kafka/HTTP/Spark stack to exercise meaningfully, and are already
covered by `make smoke` and the real `docker compose up` verification from
Phases 2-4, not by no-broker-needed unit tests.

**Known limitation**: this is statement coverage, not branch coverage,
despite `pyproject.toml` declaring `[tool.coverage.run] branch = true`. Each
service's own container runs `pytest --cov=app` from `/app/services/<name>`
— a directory that never had the repo-root `pyproject.toml` copied into it
(each Dockerfile only `COPY`s that one service's code) — so pytest-cov never
sees `branch = true` at collection time, when it matters; the combine step
running with the real config later can't retroactively add branch arcs to
data that was never collected. Fixing this for real means either copying
`pyproject.toml` into every service image or passing `--cov-branch`
explicitly on every `pytest` invocation. Deferred rather than done
speculatively in this pass — it would touch five working Dockerfiles for a
coverage-shape change with no immediate effect on the threshold decision
above, which is set against the number actually being measured.

## Security: real findings, not a rubber stamp

`make security` runs `bandit` (SAST, medium-confidence-and-severity floor)
over every service's own `app`/`event_contracts` package, and `pip-audit`
(dependency CVE scan against the free, unauthenticated OSV.dev database)
over every service's `requirements.txt`.

**bandit**: 0 medium, 0 high, across 5,878 scanned lines (29 low-severity
informational findings — not blocking).

**pip-audit**, first real run: 14 known CVEs across 4 packages.
- `pip` 25.0.1 — 5 CVEs (wheel/tar-extraction path traversal). Fixed
  outright: `pip==26.1.2` pinned as the first `RUN` step in every service
  Dockerfile and in the devtools image. Re-verified `make test` still
  167/167 after the change.
- `pytest` 8.3.3 — `PYSEC-2026-1845`, a local `/tmp/pytest-of-{user}`
  directory collision. Accepted: a test-only dependency in a single-user
  container has no other local user to exploit it.
- `pyarrow` 17.0.0 — `PYSEC-2026-113`, a C++ use-after-free. Accepted: the
  advisory itself states the vulnerable API "is not exposed in language
  bindings (Python, Ruby, C GLib)" — this codebase's pyarrow usage cannot
  reach it.
- `starlette` 0.38.6 (pulled in transitively by `fastapi==0.115.0` in all
  four HTTP services) — 7 CVEs: host-header/path confusion, HTTPEndpoint
  method confusion, two unbounded-form-data DoS variants. Accepted, with a
  verified reason, not a shrug: `pip install fastapi==0.115.0
  starlette==0.40.0` → `ResolutionImpossible` — the real fix needs a
  coordinated `fastapi`/`starlette` major-version upgrade across all four
  HTTP services with a full re-test pass, scoped as its own follow-up
  (tracked in `RISKS.md` #20) rather than a same-pass dependency bump. Also
  grepped every service: nothing reads `request.url.hostname`/`.netloc` for
  authorization (only `.path`, for logging), and the stack is local-demo-
  only, never internet-facing — both bound today's practical
  exploitability.

All 9 accepted IDs are passed to `pip-audit --ignore-vuln` explicitly (see
`IGNORE_VULN_FLAGS` in the Makefile), each with the same rationale inline as
a comment directly above it, and each pointing at `RISKS.md` #20 for the
full writeup. `pip-audit`'s own output still reports how many were ignored
on every run (`"No known vulnerabilities found, 9 ignored"`) — visible on
every CI run, not swept out of the log.

Final state: `make security` exits 0, all six scan targets report zero
un-accepted findings.

`pre-commit install` away for anyone who wants it locally.

## CI

`.github/workflows/ci.yml` mirrors `make ci` job-for-job, on GitHub's
standard free `ubuntu-latest` hosted runner (Docker + Compose v2
preinstalled) — no paid runners, no cloud credentials, no repository
secrets required. Triggers: push to `main`/`phase-*`, PRs into `main`,
manual dispatch. `coverage.xml` is uploaded as a build artifact on every
run (`if: always()`, so a failing run still leaves the report inspectable).
Workflow YAML validated for structural correctness with Python's `yaml`
parser (`actionlint`'s public Docker image was attempted but a registry
pull failed transiently mid-session; the YAML parse plus the fact that
every step is a plain `run: make <target>` — already independently
exercised locally — is the practical substitute).

## `make ci`: the full gate, run for real

`format-check → lint → typecheck → coverage → security → docker-validate →
docker-build`, in that order (fails fastest first). Final run: **exit 0,
6m50s wall time**, on this host (8 CPU / 15Gi RAM). Every number in this
document came from that run or an earlier standalone run of the same
target — nothing here is estimated (`RISKS.md` #4).

## Zero-cost compliance

No paid APIs, premium services, or paid CI runners were used. No AWS
credentials were requested or used; no `terraform apply` was run (Terraform
under `infra/terraform/` is untouched by this work — see ADR 0007). No
cloud infrastructure was provisioned. `pip-audit`'s only network dependency
is OSV.dev, a free, unauthenticated public vulnerability database, not a
paid service. GitHub Actions runs on the standard free-tier `ubuntu-latest`
hosted runner. No commit, push, merge, tag, or pull request was created by
this work.
